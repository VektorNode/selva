# Embeddable Server Layer — Tracker

**Started:** 2026-07-08 (branch `beta`)
**Context:** Selva's published packages (`@selvajs/platform`, `@selvajs/supabase-provider`) tell consuming apps to build their own stores on the engine's interfaces — the Supabase client bundle even documents it: _"a consuming app keeps `public` for its own tables"_ ([client.ts:4-10](../../packages/providers/supabase/src/data/client.ts#L4-L10)). But the API never finished that thought: the schema is hardcoded, the error mapper and pagination helpers are package-private, and the entire compute/solve server stack lives inside `@selvajs/selva` — which is a deployable app with **no `exports` field at all**. Any app built on the engine has to copy that code and re-port every improvement by hand (gzip responses, client LRU cache, rate limiting, SSRF guard — all recent, all unreachable as a library).
**Goal:** finish the "build your own app on the engine" contract: schema-aware client bundle + exported store utilities (P1–P2), then extract the compute server stack into a published package that Selva's own app dogfoods (P3).
**How to use this doc:** work top to bottom; mark Status as you go — `☐ open` / `▶ in progress` / `✅ done` / `🧊 deferred`.

The per-store boilerplate every store repeats — soft-delete filtering, audit stamping, acting-org guard — should be published helpers. Deliberately plain functions: matches how the engine's own stores are written, and a published base class ossifies a 0.x package.

| ✅     | **U3** | **`notDeleted(query)` soft-delete filter.** The `.is('deleted_at', null)` idiom repeated across engine stores, exported as a query helper.                                                                                                                                                                                                                                                                                                                                                                                                   |

**P2 implementation notes:**

- **U2** shipped as [`rowStamp.ts`](../../packages/providers/supabase/src/data/rowStamp.ts) with `stampUpdate(ctx)` and `stampSoftDelete(ctx)`. `stampUpdate` returns `{ updated_by }` (or `{}`), **not** `{ updated_at, updated_by }` as the item tentatively sketched: the engine's update paths deliberately let the per-table `updated_at` trigger set the timestamp and only stamp `updated_by` (omitted on system contexts to satisfy the `on delete set null` FK). `stampSoftDelete` is the variant that writes `updated_at` explicitly (to equal `deleted_at`). Migrated all ten hand-written `updated_by` sites and both duplicated `stampToRow` copies across Org/Project/Definition.
- **U3** shipped as [`query.ts`](../../packages/providers/supabase/src/data/query.ts) and is exported for app-owned stores. Deliberately **not** force-applied to the engine's own chains: `.is('deleted_at', null)` there sits mid-fluent-chain (after `.eq(...)`, before `.order()`/`.maybeSingle()`), where wrapping in `notDeleted(...)` fractures the chain and reads worse. The deliverable is the named, exported helper.

- Audit **D5** (unversioned `/api/compute` contract) resolves here: implement the version + response envelope **as part of K3** — the envelope is the extracted pipeline's typed return value, so designing it separately would version the contract twice. See "API contract evolution" below.
- Audit **B5** (in-process rate limiter / caches vs multi-instance) becomes a design constraint on K1/K2: keep the state behind small interfaces so a shared-store impl can slot in later without an API break.
- Audit **LB** (load-balancing groundwork: server identity as an **id**, not a URL; definition-guid routing header) must be decided **before K2 publishes** — the client-cache LRU key (`serverUrl+apiKey` today) becomes public API surface; switching the identity scheme afterwards is a semver break. - Audit **D1** (UISchema versioning / migrate-on-read for stored blobs) lands in exactly the code K4 extracts (`DefinitionService` / `loadForRender`). Decide D1 before K4, or the migration shim ships inside the package and its blob format becomes contract.
- Audit **Q4/Q5**'s compute-route test cases (share-cap at the endpoint, concurrent solve-count increments) double as the **extraction safety net**: written against the route _before_ K3, they must keep passing unchanged across the pipeline/adapter split.

## API contract evolution

As the HTTP surface grows, the contract should be a deliberate artifact, not ad-hoc SvelteKit routes:

- **Typed client SDK** (P3 follow-on): export a typed client from the same package, types derived from the existing Zod route schemas (or OpenAPI generated from them). This is the same single-schema philosophy as `ui-schema.json` → TS + C#, and it resolves audit D5 by making the compute contract an explicit, versionable type.
- **GraphQL: explicitly deferred.** The core endpoint is RPC-shaped (inputs → solve → results/geometry), the entity graph is shallow, and GraphQL would forfeit the transport-level wins (gzip + Server-Timing, binary payloads, HTTP caching) while adding query-complexity/security work. K3's transport-agnostic pipeline keeps the door open: any transport can wrap the package later if a real multi-client need appears. Revisit only when there are several third-party consumers composing queries.

## Non-goals

- **No published base class for stores** — helpers only (see P2 rationale).
- **No bolting `exports` onto `@selvajs/selva`** — app internals are entangled with `$env`/`$app` and would become an accidental semver surface. The library is the new package.
- **No third-party store registration into `SelvaConfig`/`IDataProvider`** — the engine's data contract stays the engine's; apps compose their own stores beside it. The public story is `clientBundleFromEnv` + `forRequest(ctx, { schema: 'public' })` + the P2 helpers, which gives app stores the same RLS/context discipline as engine stores for free.

P3 is the real extraction — K1/K2 are mechanical once env injection is threaded; K3 is the careful one (the 589-line handler needs a policy/pipeline split); K4–K5 wait until the package boundary has settled against real usage.
