## Priority model

Ranked by **cost of fixing later ÷ cost of fixing now**, not by severity. Three things drive an item up:

1. **Irreversibility** — once rows/links/clients exist, the fix needs a migration or a compat shim. Cheap today, expensive at 100 users.
2. **Correctness with a live failure mode** — it can serve a wrong answer or corrupt state, at any scale.
3. **Load-bearing for scale work** — other planned work sits on top of it.

Everything else is efficiency, hygiene, or a decision to record. Real but not urgent.

## C. Solve cycle

Full trace: input change → debounce → client throttle/memo → `POST /api/compute` → route (auth/rate-limit/DB/byte-cache) → single-flight → pipeline (L2 → scheduler L1 → pointer solve → Rhino `cachesolve`) → serialize/gzip → response → parse → three.js render.

**Verdict:** the cache layering is sound and consistently keyed (immutable version ids, org-scoped L2, `algo`-stripped responses, lazy `DefinitionRef`, latest-wins client throttle). Worth keeping: async gzip off the event loop, gzip-at-rest L2 hits that skip stringify entirely, streamed size-capped remote fetch, definition hashed once per solve, error contexts that summarize instead of pinning multi-MB trees. The items below are the gaps.

- **C1 — ✅ Done 2026-07-16.** Both defects fixed in `solveMemo.ts`. The root cause was an **ownership** conflict: the viewer takes ownership of every mesh array it renders (`updateScene` → `clearScene` disposes the previous content), while the memo simultaneously retained those same instances. Two owners, one lifetime.
  The memo now owns private copies and shares nothing: `set` stores a deep clone, `get` returns a fresh clone per hit, and every path that drops an entry (LRU eviction, `clear()`, and **key overwrite** — a third leak the audit missed) disposes its geometry first.
  **Took the audit's second option, not its recommendation.** "Memoize the parsed response and rebuild meshes on hit" was the stated preference, but it isn't reachable from the memo: meshes are built by `extractMeshesFromResponse` in the _app's_ solve fn (`library/[guid]/+page.svelte:188`), above the memo in `@selvajs/ui` — the memo only ever sees a finished `SolveResult`. Rebuilding would mean restructuring the solve fn across a package boundary. Clone-on-hit + dispose-on-evict achieves the same invariant (the memo never shares a GPU object with the scene) inside one module.
  **The clone had to be deeper than it looks.** `Object3D.clone()` copies the transform hierarchy but **shares `geometry` and `material` by reference** — the exact aliasing being fixed — so geometry is cloned explicitly per node. Materials are left shared on purpose: `clearScene` skips disposing anything in `SHARED_MATERIALS` (module-scope singletons reused across solves, `three-materials.ts:145`), and cloning them would multiply shader programs. Disposal mirrors that split — geometry only, never materials.
  **Why it survived this long:** every pre-existing memo test used mesh-free results (`{ outputs: { out: tag } }`), so the suite never touched the field that breaks. Added 7 tests covering the real shape. Verified both directions: the clone tests fail against the old code, and the disposal tests fail if the dispose calls are removed. 90/90 `@selvajs/ui` tests + `svelte-check` clean.
- **C5 — Coalesced waiters inherit the first caller's `Content-Encoding`. [P1]** The coalesce key (`api/compute/+server.ts:336`) is `org:version:inputs` — **`Accept-Encoding` is not in it**. The envelope is built inside the coalesced work from the first caller's header (`:350-366`, `solve-pipeline.ts:431`) and `solve-cache-single-flight.ts:53-54` hands that same promise to every waiter. A non-gzip client joining a gzip client's flight gets a gzip body labeled `Content-Encoding: gzip`; `Vary` (`:414`) doesn't help because this is one object handed to mismatched waiters, not a cache lookup. Latent today (browsers all send gzip) but it is a **wrong response**, not a slow one — it lands the moment a non-browser API consumer exists, which the D5 contract work invites. Fix: key coalescing on encoding, or re-encode per waiter from the stored gzipped body.
- **C2 — Scheduler L1 has no byte budget. [P1]** `client-cache.ts:229` → `{ maxEntries: 20, ttlMs: 5min }` per warm client; the scheduler evicts on `this.cache.size > this.cacheMax` (`solve-scheduler.ts:900`) — entry count, never bytes. Worst case is 20 × `computeResponseMaxBytes` (**currently 300 MB**, see B3) × up to 16 warm servers, holding _uncompressed_ objects that duplicate what L2 keeps gzipped. It is the only cache in the stack bounded by count: the definition-byte cache (`definition-byte-cache.ts:21-27`) and the L2 backstop are both byte-aware. Give it the same bound.
- **C3 — Redundant input-tree serialization. [P2]** Server, per fresh solve: coalesce key (`api/compute/+server.ts:336`), L2 key (`solve-cache-key.ts:78` via `solve-pipeline.ts:246`), scheduler hash (`stable-hash.ts:148`), wire body (`compute-fetch.ts:797`), plus response `JSON.stringify` (`solve-pipeline.ts:325`) — 5 linear passes over a potentially MB-scale tree. Client adds 4: memo key twice (`solveMemo.ts:17`, get + set), payload stringify (`library/[guid]/+page.svelte:72`), and an **unconditional** `JSON.stringify(values).length` whose only use is a log line (`:81` → `:238`, `:253`) — a full serialize thrown away every solve. Past 256 KB a whale loop re-stringifies every input on top (`:243-246`). **Cheapest win: delete the unconditional size log** (or gate it behind the debug flag). The rest: derive one canonical string per boundary and thread it through — the L2 key and scheduler hash already share `stableStringify` and parity is a stated requirement, so reuse is safe by design.
- **C4 — Hot-path reads per solve. [P2]** **5 sequential awaited DB reads** on the common logged-in path, 7 with a share link: `tryResolveShareToken` (`:140`), `definitions.get` (`:201`), `projects.getProject` (`:209`), access check (`:217`/`:222`), `definitions.getVersion` (`:232`), `tryIncrementSolveCount` (`:274`), `resolveServerForOrg` (`:285`). Bytes and warm clients are cached; the records are not — so a same-definition slider re-solve pays all of them. Dovetails with 4b.
  **Also a false comment:** `:177` reads _"Per-key rate limit; runs before DB reads so throttled callers don't burn quota"_ — but `tryResolveShareToken` (`:140`) is an awaited DB read ~37 lines earlier, and it must be, since the rate key at `:178` derives from `sharedAccess.link.id`. Either pre-key on the raw token to make throttled share callers genuinely DB-free, or fix the comment. Do not leave it claiming a property it doesn't have.
- **C6 — L1 hits still pay full serialize + gzip. [P3]** `solve-pipeline.ts:349` gates the skip on `willCache = args.solveCache != null`; the early return at `:253-261` needs L2. So a **scheduler-L1 hit with no L2 hook** (draft channel, quota-0) skips Rhino but still runs `JSON.stringify` (`:325`) and gzip (`:354`) per request. `settle.fromCache` is available but only read afterwards for telemetry (`:382`). The L2 path proves it's avoidable.
- **C7 — L2 collision defense is documented, not implemented. [P3]** `solve-cache-key.ts:7-8` promises the entry stores the canonical preimage "so a hit can compare it byte-for-byte (defense-in-depth)", and `:53-55` types `SolveCacheInputKey.canonical` for exactly that. But `EnvelopeHeader` (`solve-cache-envelope.ts:22-36`) has no `canonical` field, `solve-pipeline.ts:246` discards the preimage at derivation, and the hit check (`:472`) compares `inputHash` to `inputKey` — digest to digest, tautological against the storage key. It catches corruption, not the documented collision class. SHA-256 collisions aren't a real threat, so **fix the doc, not the code** — and drop the dead `canonical` field from the return type.
- **C8 — Decision note: share-cap burns on failed solves. [P3]** `tryIncrementSolveCount` runs before the solve (`:272-283`, comment: "run before solve to avoid wasting compute") and is refunded on no failure path — `timeout` (`:371`), `client_abort` (`:375`), `too_large` (`:379`), `shed` (`:387`), `compute_error` all error out without decrementing. Defensible (refunds invite cap-bypass via induced failures), but `shed` is the sharp edge: it's an explicitly retryable 503 where the solve never reached compute, so a well-behaved client backing off and retrying pays each time. **Confirm intended, like D6.** Related for Q5.2: local's whole-file read-modify-write means a concurrent `revoke` racing an increment can be _lost_ entirely, not just over-counted.

## B. Scaling roadmap

Assumption: 1000 registered users ⇒ Supabase provider, adapter-node behind a reverse proxy, one+ Rhino.Compute servers. Realistic concurrency ~50–150 active sessions, slider-scrubbing solve storms as peak load. **Verdict:** web tier + Postgres are fine once the audit items land; the real ceiling is **Rhino.Compute capacity**.

- **B3 — ✅ Done 2026-07-16.** Reverted the two TEMP dev raises in `resolveComputeLimits`: `maxGhFileSize` 300 → **50 MB**, `computeRequestMaxBytes` 300 → **210 MB**. The stale TEMP note in the app shim is gone; the sizing rationale now lives on the `ComputeLimits` fields themselves, where the values are. Solve payloads are still fully buffered base64 through the heap (`limits.ts:96-107`) — these caps are the backstop, ADR 0003 streaming is the real fix.
  **Correction — the response cap was never a TEMP value.** Both this audit and the TEMP note implied all three caps were raised. Git says otherwise: pre-extraction (`f7d18660^`) the app carried exactly **two** TEMP markers — `MAX_GH_FILE_SIZE` (50 → 300 MB) and `COMPUTE_REQUEST_MAX_BYTES` (210 → 300 MB). `COMPUTE_RESPONSE_MAX_BYTES` had none: **300 MB is its intended value**, sized above any legitimate inline payload and below V8's ~512 MB string wall, and it is _not_ bounded by `BODY_SIZE_LIMIT` (which only covers inbound bodies). Reverting it to 210 MB — as the note's "50 MB / 210 MB" phrasing invited — would have been a regression. Now documented as deliberate so the next reader doesn't "fix" it.
  **The numbers weren't arbitrary, and now they're checked.** `.env.example` is the sizing source: `BODY_SIZE_LIMIT=210M` ships as the global adapter-node cap, so a request cap above it is dead config (the global backstop rejects first); 50 MB matches Rhino.Compute's own `RHINO_COMPUTE_MAX_REQUEST_SIZE` default, past which uploads 413 at compute anyway.
  **Root cause addressed:** `resolveComputeLimits` had **zero tests** — the only thing tracking the raise was a comment nobody re-read, which is how it reached a release branch. New `__tests__/limits.test.ts` (17 tests) pins the defaults _and_ the invariants that justify them (remote-definition lockstep, request cap clears a base64-inflated 150 MB upload, every cap under the V8 wall). Verified the gate bites: re-raising upload to 300 MB fails the suite. 263/263 package tests green.
- **B9 — `solve_metrics`: one unbatched INSERT per solve attempt. [P1]** `SupabaseSolveMetricSink.ts:18` — one `.insert()` per `record()`, no batching, no queue, no flush timer (awaited, errors swallowed by contract at `:9-11`, `:31-36`). Slider scrubbing at ~100 active users ⇒ hundreds of inserts/sec against the same Postgres serving auth. Fix: buffer + periodic batch flush behind `ISolveMetricSink`, or sample non-error metrics under load — keep failures unsampled, they feed alerting.
- **B5 — Rate-limit buckets never evict. [P1]** `packages/server/src/compute/rate-limit.ts:71` — `new Map<string, BucketEntry>()`, entries only created (`:80`) or overwritten when expired (`:79-81`). No sweep, no cap, no `setInterval`; `clear()`/`reset()` (`:103`, `:106`) are login-forgiveness/test seams, never production pruning. A key seen once stays resident forever. Growth is slow (bounded by distinct `user:{id}`/`share:{linkId}` keys) but unbounded. Add a periodic sweep.
  **Correction to the previous doc:** the sibling caches it accused are all bounded — `remote-definition.ts:138-143` evicts oldest-10 past `CACHE_MAX_ENTRIES = 50`; `client-cache.ts:154` is an LRU with `maxEntries` 16 that disposes schedulers on evict (`:300-305`); there is no separate getIO cache (getIO shares the warm client entry, `:22`). The rate limiter is the _only_ unbounded one left.
  Multi-instance drift is the other half: per-instance buckets ⇒ N× effective rate (acknowledged at `rate-limit.ts:8-11`); per-instance caches are fine. Decide: accept N×, or move the limiter to Redis.
- **B1 — Rhino.Compute saturation (the real ceiling). [P2]** Selection is one config per org, narrowest-wins: definition pin → org default → global default (`platform/src/computeServer/utils.ts:66-86`, app wrapper `resolve.server.ts:37-47`). Mitigations are good (client throttle, rate limit, `cachesolve`, pointer reuse). Missing: queue/backpressure UX (users see hangs, not "#4 in queue"); a compute _pool_ (one busy org saturates its single server); cross-instance admission control (one `SolveScheduler` per warm client, in-process — `client-cache.ts:217`, acknowledged at `limits.ts:139-146`); per-org metering/quotas.
- **B2 — Auth: GoTrue round-trip per request. [P2]** Fixed for the request path already; flagged here as scale-mandatory — revisit revocation-latency design under real load.
- **B4 — Database hot spots. [P2]** Missing indexes (4g). Audit events grow unbounded — need retention/partitioning before the admin audit page and inserts degrade. `definition_versions.schema` JSONB bloat (4b). `recordRun` per solve (4d) becomes required, not nice-to-have, at volume.

**Missing production-grade features (beyond efficiency):** async solve jobs (long solves die at proxy timeouts and on deploy — need a job queue + polling or SSE); aggregated observability (latency percentiles, queue depth, compute utilization, error-rate alerting); graceful shutdown / zero-downtime deploys; load testing (nothing exercises concurrent solve load — k6/artillery scenario needed); backup/DR for storage buckets (Postgres PITR covered, blobs are not); abuse surface on public share links (per-IP limits, CAPTCHA at scale).

## LB. Compute load balancing

- **LB-1 — `X-Selva-Definition` is stale on warm clients. [P2]** The header is baked in `build(server, definitionGuid)` (`client-cache.ts:212-214`), which runs only on a cache **miss** (`:295`); a hit returns the existing entry (`:288-290`) and ignores `opts.definitionGuid`. So the header freezes to **the first definition to touch that server** and is then stamped on every later solve for every other definition on that client. The code notes it's "inert for a single-member pool" (`:209-211`) — but it is not inert for its one stated use _today_: compute-side access logs are actively wrong. And it **mis-routes** the moment an affinity router keys on it, which is the entire point of the header. Fix needs a per-request header hook in the scheduler (same wall K6 hit and cleared by threading per-solve options through `scheduler.solve`) — that pattern is now proven, so this is unblocked.

**Routing law when the time comes:** solves route by definition affinity (hash guid → pool member). Both the pointer cache and `cachesolve` key on the definition, so naive round-robin divides hit rate by N and can trigger the silent-empty-geometry failure mode (`computeLimits.ts:138-144`). Recommendation: app-level pooling over an infra LB — the app already holds per-server schedulers with queue-depth awareness, the API-key-per-server model doesn't fit a shared LB URL, and per-org quotas want the same decision point.
