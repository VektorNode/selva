# Solve transport bench: measure before choosing

**Unfiled.** Design only.

Several fixes compete for the same slow solve: keeping documents warm (session affinity), building
files only on download, deduping unchanged output items, splitting materials from geometry, and
moving geometry out of the JSON. A first capture on the timber gridshell showed why guessing fails.
A beam-colour change ran 6 of 781 objects in 0.47 s of Grasshopper, yet took about 6 s in the
browser, because every solve shipped 29.6 MB: a 19.4 MB 3DM, a 7.8 MB mesh in one display item and
a 1.7 MB PDF. Affinity was working; the payload was the problem.

This plan is one definition built to isolate each cost, and one harness that records every solve
the same way, so each decision below rests on numbers.

## The definition

`dev/grasshopper/bench-solve-transport.gh`, generated by `SolveBench.cs` beside `Stress.cs` in
`scripts/plugin/example-definitions`, so it is rebuilt rather than rewired when a component
changes. Each input feeds one part of the graph, so changing it says exactly what re-runs and what
re-ships.

| Input                           | Feeds                                                    | Isolates                                              |
| ------------------------------- | -------------------------------------------------------- | ----------------------------------------------------- |
| Upstream work (0–10 s)          | a fixed-cost step every geometry depends on              | warm vs cold: a warm solve of anything below skips it |
| Shape                           | the parametric mesh                                      | a geometry change                                     |
| Mesh size (1–60 MB on the wire) | the parametric mesh's density                            | where transport starts to dominate; the 50 MB case    |
| Display branches (1–32)         | how the parametric mesh splits into Web Display branches | whole-item dedupe per branch                          |
| Shape scope (branches)          | how many branches a Shape change touches                 | dedupe when only part of the scene changes            |
| Context size (0–50 MB)          | a mesh no input changes, in its own branch               | dedupe of a static branch                             |
| Colour                          | the parametric mesh's material only                      | the material/geometry stream split                    |
| Files (off, on)                 | a 3DM of the panels; off, a 3DM of one point             | building files on demand                              |
| —                               | the face count as a number                               | the floor: a solve that ships almost nothing          |

Upstream work needs a step that takes a set time and nothing else. A C# Script that sleeps is
exact; a stock chain only approximates it. The geometry is C# Scripts too, so its size can be set
in megabytes. A Display's wire size is the length of its goo's `ToComputeJson`. These jittered
grids measure about 2.9 characters per quad face, so Mesh size 5, 20 and 50 give 4.8, 18.8 and
46.7 MB. The jitter matters: a perfectly regular grid deflates to almost nothing. The 3DM tracks
Mesh size; a PDF was left out because its cost is the drawing, not the transport.

## The harness

`scripts/develop/solve-bench/`, three pieces, committed so a number can be reproduced:

- **Capture proxy.** It sits between Selva and compute (point the compute server URL at it) and
  writes one JSONL row per solve. Each row holds the inputs, the session (mapped to user and
  definition), and compute's `Server-Timing`: decode, gh, harvest, encode and recomputed. It also
  holds bytes per output, and how many of those bytes were identical to the same session's previous
  two solves, per output and per branch. That last figure is what a whole-item dedupe would skip.
  It works on any definition, so a real project is measured by clicking through it with capture
  on.
- **Runner.** It drives scenarios through Selva's solve API as real users, so the session header,
  Selva's caches and its gzip are all in the path. It adds Selva's own timings from the response
  (solve, serialize, gzip, total) and the routing outcome from compute's Debug log.
- **Browser timing.** The time from an input change until the viewer has drawn, through Playwright
  against `dev:local`. The server-side rows can't see download, parse and mesh decode. On the
  gridshell, that unseen part was about 2.5 s of the 6.

Captures hold input values, so they stay out of git. Run on `dev:local` data.

## Scenarios

1. **One user, one input class at a time.** The cost of a colour, shape, size or files change,
   split into Grasshopper, compute encode and transfer, Selva gzip, and browser.
2. **Mesh size sweep, 1 to 60 MB, at a fixed change.** Where each stage's share crosses over.
3. **Two users alternating, signed in vs share link.** Affinity against the no-header baseline.
4. **More users than children (three users on two children).** How often they evict each other's
   documents, which decides whether the child document pool is worth its memory.
5. **Idle ten minutes, then solve.** Reproduces the children that returned empty outputs, with no
   errors, after sitting idle.

## What each number decides

| Decision                                               | Settled by                                                                |
| ------------------------------------------------------ | ------------------------------------------------------------------------- |
| Build files only on download                           | share of bytes and time from file outputs, across real clicks             |
| Whole-item dedupe, server to browser                   | unchanged bytes per solve, branches 1 vs many, scenario 1 and real clicks |
| Material/geometry stream split                         | the colour change at 50 MB, scenarios 1 and 2                             |
| Geometry out of the JSON, or stripping the compute hop | encode, harvest and transfer share at 50 MB                               |
| Affinity tuning and the child document pool            | warm/cold rates in scenarios 3 and 4                                      |
