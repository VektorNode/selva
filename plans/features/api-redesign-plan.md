# Plan: API v1 redesign — one versioned surface for browser + tokens

## Context & decision

The current `/api/*` surface is internally consistent (uniform `apiError`/`ApiErrorCode` envelope,
guards from `access.server.ts`) but was grown as a browser-mutation API: **all list/detail reads
live in page load functions**, two endpoints have unconventional method semantics, and org-scoped
naming is inconsistent. The PAT/public-API plan ([token-plan.md](token-plan.md)) needs a stable
contract on top of this.

**Decision (supersedes token-plan Phase 4's wrapper approach):** Selva is pre-launch with zero
external API consumers — so instead of freezing the current shape behind `/api/v1` wrappers, we
redesign the API once, now, as a **single versioned surface `/api/v1/*` used by both the browser UI
and API tokens**. One implementation, one contract, continuously dogfooded by our own UI. Stability
is expressed per-endpoint in the OpenAPI spec (`x-internal` tags), not by maintaining two URL trees.

Migration cost is small and fully in-repo: **48 `fetch()` calls across 21 files** in
`packages/selva/src`. Of these, **46 are string literals across 20 files** (26 under `/api/*`, 20
under `/admin/api/*`) — that 46 is the number to write grep gates against. The remaining 2 are the
`AssetUpload.svelte` pair, built from a `$derived` `endpoint` variable at
[AssetUpload.svelte:24](../../packages/selva/src/lib/components/AssetUpload.svelte#L24) and consumed
at lines 48 and 66; **no literal-based find-replace will catch them.** Two further `fetch()` hits in
`/api`-pathed server files are outbound calls to external compute hosts, not API callers, and are
excluded. `packages/cli` has no Selva API call sites (its only two `fetch()` calls are Supabase
health probes in `doctor.js`), though its CHANGELOG does mention `/admin/api/`. Phase A still
includes a repo-wide grep for constructed (non-template-literal) URLs.

`/api/files` URLs are **not** in that count and must not be: they are generated by the storage
providers ([LocalStorageProvider.ts:19](../../packages/providers/local/src/storage/LocalStorageProvider.ts#L19),
[SupabaseStorageProvider.ts:73](../../packages/providers/supabase/src/storage/SupabaseStorageProvider.ts#L73))
and persisted into rows, so that prefix is a data format, not a UI convention — see "Deliberately
outside v1".

### Follow-ups this plan deliberately does not do

Recorded so they are decisions rather than omissions:

- **Wire up anonymous sharing** — needs a hook carve-out for `/library/{guid}` + `/api/compute`
  and `+page.svelte` threading `data.shareToken` into the solve fetch. Currently two unfinished
  halves of a feature whose server layer is complete. Unblocked by this plan, not part of it.
- **Fix the instance-admin org fallback** — order by `createdAt asc` with an id tiebreaker, or

## Conventions (normative — every v1 endpoint follows these)

### Paths

- `/api/v1/<plural-resource>[/{id}[/<sub-resource>|/<action>]]`.
- **Org-scoped resources are explicit**: `/api/v1/orgs/{orgId}/…` (members, invites, compute
  settings). Tenancy invariant stays as implemented today in
  [orgs/[orgId]/members/[userId]/+server.ts](../../packages/selva/src/routes/api/orgs/%5BorgId%5D/members/%5BuserId%5D/+server.ts):
  the URL `orgId` **must equal `ctx.actingOrgId`** (403 otherwise). Explicit IDs future-proof for
  the planned URL-prefix tenancy (`/o/{slug}` note in hooks.server.ts) without changing the API.
- **User-scoped resources** under `/api/v1/me/…` (starred; profile later).
- **Actions** (non-CRUD verbs) are `POST /api/v1/<resource>/{id}/<verb>` — `publish`, `reclaim`,
  `solve`, `disable`. Documented in OpenAPI as actions, not resources.

### Methods & status codes

| Method   | Use                                                       | Success                    |
| -------- | --------------------------------------------------------- | -------------------------- |
| `GET`    | Read; never mutates                                       | `200` + resource / page    |
| `POST`   | Create (`201` + created resource) or action (`200`/`202`) | `201` / `200`              |
| `PATCH`  | Partial update (all our updates are partial)              | `204`, or `200` + resource |
| `PUT`    | Idempotent full set **only** (`/me/starred/{guid}`)       | `204`                      |
| `DELETE` | Delete / revoke                                           | `204`                      |

No `PUT` for partial updates — the two current offenders both move to `PATCH` (their handlers
already have merge semantics: `PUT /api/org/compute` documents "`undefined` leaves it untouched").

### Errors

The existing envelope from [api-errors.ts](../../packages/selva/src/lib/server/api-errors.ts)
(`ApiErrorCode`, `apiError`, `handleApiError`) is the v1 contract. Every code gets documented in
the OpenAPI spec. No route may return a bare `error(...)` — already true for all 40 route files;
a conformance test keeps it that way (Phase D).

Two additions for external consumers:

- **`requestId` goes into the error body.** The hook already computes a correlation id and echoes
  it as a response header; putting it in the JSON envelope turns "my solve failed" reports into
  one-grep log lookups. Cheap now, painful to retrofit onto a published shape.
- **Existence is never leaked.** A resource the caller cannot see returns `404`, not `403` — a
  public API invites cross-tenant guid probing on `/api/v1/definitions/{guid}`. `403` is reserved
  for "you can see this exists but may not do that" (e.g. the tenancy mismatch on
  `/orgs/{orgId}/…`). Today's handlers are mixed; normalize during Phase A/B and pin it in the
  Phase D conformance test.

Reserve the rate-limit surface now, even though enforcement lands in the token plan: `429` in
`ApiErrorCode`, `Retry-After` + `RateLimit-*` headers documented in the spec. Adding a status code
to a published enum later is a breaking change; reserving it is free.

### Response envelope

**Collections return `{ items: T[], nextCursor?: string }`. Single resources return the resource
object bare.** No resource-named keys — `{ items: [...] }`, never `{ projects: [...] }`; the project
object itself, never `{ project: {...} }`.

This is a change from today: `GET /api/projects` currently returns `{ projects: page.items }`,
discarding the `Page<T>` the store already handed it. A resource-named key forces every client —
UI, CLI, MCP — to write one unwrapper per endpoint instead of one pagination helper for the whole
API. Phase A rewrites these call sites anyway, so the cost of fixing it is close to zero now and
grows with every consumer added later.

### Pagination

Cursor-based, straight from the platform layer
([pagination.ts](../../packages/platform/src/pagination.ts)): query params
`?limit=&cursor=&orderBy=&orderDir=` → response `{ items: T[], nextCursor?: string }`.
Limits clamp to `MAX_PAGE_LIMIT` (200), default 50. Cursors are opaque. Every list endpoint —
no unpaginated collections in v1. `GET /api/projects`'s hardcoded `limit: 200` with no cursor
pass-through is the current offender; it becomes a normal paginated list.

### Idempotency

`POST /api/v1/definitions/{guid}/solve` accepts an optional `Idempotency-Key` header. A repeated
key within the retention window returns the first response instead of re-solving. Edge semantics
follow the IETF idempotency-key draft: same key + different request body → `422`; a replayed
response carries an `Idempotency-Replayed: true` header so clients can tell cache from fresh solve.

Solve is the one action with real per-call cost, and its two biggest non-browser consumers both
retry by nature: a CLI wrapping a flaky network, and an LLM re-issuing a tool call it thinks
failed. Without a key, both double-charge compute. Retrofitting this after PATs ship means changing
a published contract, so it lands with the endpoint. Scope for v1.0: in-memory store keyed by
`(tokenId|userId, key)`, short TTL — enough to absorb retries, not a durable result cache. The
store is **per-process**: correct for the single-instance PM2 deployment, silently useless the day
a second instance runs. State that constraint in the spec so scaling out is a known trade, not a
surprise.

### Stability & change policy

- Every endpoint is either **public** or **`x-internal`** in the OpenAPI spec. `x-internal`
  endpoints are excluded from published docs and may change without notice.
- Public endpoints: **additive-only** within v1 (new optional fields/params OK; no removals,
  renames, type or semantics changes). Breaking change ⇒ new route under `/api/v2` alongside.
- **Deprecation policy, one paragraph in the spec:** removals require v2; anything deprecated
  within v1 gets a `Deprecation` header and stays functional for a stated window. Additive-only
  tells consumers what we won't do — this states what happens when we eventually must.
- **CORS: none on `/api/v1` in v1.0.** The surface is same-origin browser + non-browser PAT
  callers. Stating it explicitly preempts the recurring "your API is broken from my SPA" report;
  relaxing it later is additive.
- Uploads (definition create, version upload, image) are `multipart/form-data`; documented as such.

### Auth & the two scopes

The API has exactly two scopes, and the URL says which one you're in:

| Prefix         | Scope                               | Credentials       | Versioned |
| -------------- | ----------------------------------- | ----------------- | --------- |
| `/api/v1/*`    | Tenant — acts as the caller's `ctx` | Cookie **or** PAT | Yes       |
| `/api/admin/*` | Platform — instance administration  | Cookie **only**   | No        |

- `/api/v1/*` is the _only_ prefix that accepts `Authorization: Bearer sk_…`. The token-plan gates
  on `pathname.startsWith('/api/v1/')` exactly, so this stays an unconditional prefix test with no
  carve-outs inside it.
- **`/admin/api/*` moves to `/api/admin/*`** (Phase A). Same handlers, same session-only treatment,
  same per-handler platform guards (`requireInstanceAdmin` and siblings — see "Deliberately outside
  v1"). What changes is that all HTTP endpoints live under one `/api` root and `/admin` becomes
  purely the page tree.
- `/api/health` stays unversioned (LB probe, allowlisted in the route classifier).

Why the split is by scope and not folded into one tree: `/admin/api/projects` lists **every org as
`SYSTEM_CONTEXT`**, while `/api/projects` lists **the acting org as the caller**. Same resource
name, deliberately different reach — not duplication to merge. Putting admin inside `/api/v1/*`
would make instance administration bearer-reachable by default and require an exception inside the
prefix that is supposed to be uniform.

**Known gap this move does not fix:** `/admin/+layout.server.ts` guards page loads only — SvelteKit
does not run layout loads for `+server.ts`. Admin endpoints are protected solely by their own
`requireInstanceAdmin` call. True today, true after the move; the Phase D conformance test is what
turns it from convention into something enforced.

### Auth mechanics — why one handler serves both credentials

**The pipeline below the hook is already credential-agnostic, and that is what makes this plan
cheap.** Every guard in [access.server.ts](../../packages/selva/src/lib/server/access.server.ts)
takes `locals` and reads `locals.ctx` / `locals.user` — `requirePermission(locals, permission)` and
~30 siblings. None of them touches a cookie. So a PAT branch in `hooks.server.ts` that populates
the same `locals.user` + `locals.ctx` makes every v1 route bearer-capable with **zero handler
changes**. The 401-vs-303 split already exists (`isJsonApiRoute` — a local response-shape selector
at [hooks.server.ts:251](../../packages/selva/src/hooks.server.ts#L251), _not_ an auth decision and
not exported), so bearer callers get JSON errors rather than login redirects.

That is the load-bearing claim behind "one implementation, two credentials". It holds — with three
consequences that belong in the token plan's Phase 2, not discovered during it.

**1. A PAT's org is resolved per request, not frozen at mint time.**
[`buildContext`](../../packages/selva/src/hooks.server.ts#L108-L138) derives `actingOrgId` from
`findUserMembership`, so a token inherits whatever org its minting user belongs to _at call time_.
If their membership changes after minting, the token's reach changes with it. This is consistent
with token-plan's intersection rule (a PAT never widens permissions), but it means **a PAT is not a
stable tenant credential** — do not document it as one.

**RESOLVED — PATs carry an explicit `orgId`; minting is rejected when the user's only org is the
admin fallback.** The `instance_admin` fallback
([hooks.server.ts:130-137](../../packages/selva/src/hooks.server.ts#L130-L137)) is worse than "an
arbitrary org", which is why the permissive option is off the table:

- It calls `listOrgs(SYSTEM_CONTEXT, { limit: 1 })` with **no `orderBy`**, and both providers
  default to `createdAt` **desc** ([pagination.ts:40-41](../../packages/providers/local/src/data/pagination.ts#L40-L41),
  [SupabaseOrgStore.ts:49-58](../../packages/providers/supabase/src/data/SupabaseOrgStore.ts#L49-L58)).
  "The first org" is the **most recently created** one — the comment says the opposite.
- So the acting org **silently changes the moment anyone creates a new org**. Under `created_at`
  ties Supabase has no tiebreaker and the result is genuinely non-deterministic.
- `orgPermissions` stays `[]` in this branch — the admin acts _in_ an org with zero org-level
  permissions, relying purely on platform permissions.
- There is **no org switcher**, and the root layout exposes only a bare org id
  ([+layout.server.ts:27-33](../../packages/selva/src/routes/+layout.server.ts#L27-L33)) — an admin
  cannot tell which org they are acting as without visiting `/team`.

A bearer credential whose tenant re-resolves on every call and flips when an unrelated org is
created is not a credential. `GET /api/v1/me` returns `actingOrgId` so a holder can always
introspect what they resolved into.

The fallback's non-determinism is a **pre-existing bug worth its own fix** (order by `createdAt asc`
with an id tiebreaker, or refuse to guess) — it is out of scope here, but it must not become a
token's tenancy. Note the fixture at
[fixtures.ts:557-562](../../packages/selva/src/lib/server/__tests__/fixtures.ts#L557-L562)
faithfully mirrors the production logic, so tests will not catch the ordering quirk.

**2. The hook does four DB reads per authenticated request.** `ensureUser` + `getProfile` +
`getFor` + `findUserMembership` run in one `Promise.all` — tuned for browser navigation, where it
happens once per page. For a CLI looping `solve` or an MCP tool issuing repeated calls it is four
reads of per-call overhead; only `ensureUserOnce` is memoized. Not a blocker and not this plan's
job to fix, but the PAT path should either cache the resolved context per token id or skip
`getProfile` outright — display name and starred list are meaningless to a bearer caller.
Note the four-read block exists **twice** in `hooks.server.ts` — the gated path
([:361-366](../../packages/selva/src/hooks.server.ts#L361-L366)) and the best-effort attach for
public pages / self-gating routes ([:418-423](../../packages/selva/src/hooks.server.ts#L418-L423)).
Any change to context building (this plan's classifier collapse, token-plan's PAT branch) touches
both copies or deliberately leaves one alone — say which.

**3. Invariant that keeps the prefix test unconditional:** _every `/api/v1/*` route requires a
fully-populated `locals.ctx`; anything that cannot is not a v1 route._ The clean
`startsWith('/api/v1/')` gate is only clean because every anonymous-capable endpoint lives
**outside** v1. Admitting one into v1 would force a carve-out inside the prefix that bearer auth is
applied by — exactly the uniformity the split exists to protect.

**Blocker #5 resolved this by growing the exception set from one to two, not by weakening the
invariant.** Anonymous-capable, all outside v1:

- `/api/files/[...path]` — serves public branding to guests, 401s on org assets
- `/api/compute` (+ `/api/compute/schema`) — the share-token solve path. Share links are anonymous
  by design (six independent spec/doc/test sources; see blocker #5), so this route is destined to
  become self-gating. It stays unversioned rather than being admitted to v1 and later contradicted.

The PAT branch must in any case **pass through** non-`sk_` bearer tokens rather than reject them —
share tokens ride the same `Authorization: Bearer` header.

  purpose. A test proves the credential cannot get through even when present on the input, and that
  a later-added field is dropped.

Also: `PATCH /orgs/{orgId}/compute` was the last handler validating its body by hand (a cast to a
TS interface plus manual checks). It is now `OrgComputePatchBodySchema`, so the spec derives that
body too. Its `apiKey` is deliberately `.nullable().optional()` and **not** `.nullish()` — omitted
keeps the stored key, `null` clears it, a string replaces it, and collapsing the first two would
wipe a live credential on any save that left the field out. A test pins the three-way distinction.

Verified: `pnpm type-check` (22/22), `pnpm check` (0/0), `pnpm lint` (0 errors; the new and changed
files lint completely clean), `pnpm test` (353, up from 343), plus a production build.

Not done, recorded rather than silently dropped: **`Cache-Control: private, no-store` on v1 GET
responses.** Carried from earlier phases and still open — a PAT-reachable API returning
tenant-scoped JSON with no explicit cache header risks a proxy caching an authenticated response.
It is a one-line hook change plus a conformance assertion, but it changes response headers on every
read endpoint, which is its own PR.

1. **OpenAPI spec** `packages/selva/openapi/v1.yaml`: all v1 endpoints, auth schemes (cookie +
   bearer), scopes (from token-plan), pagination params, full `ApiErrorCode` enum, `x-internal`
   tags. **Derive the request/response schemas from the Zod validators** (e.g. `zod-openapi`)
   rather than hand-writing them — the conformance test below catches route/path drift but not
   _shape_ drift; a renamed response field in a hand-transcribed spec slips through silently. The
   validators are already the source of truth; the spec should be generated from them, with the
   yaml holding only what Zod can't express (descriptions, examples, `x-internal`).
2. **Conformance test** (vitest) — enforces the contract, not just its existence. Enumerate
   `routes/api/v1/**/+server.ts` exports and assert:
   - every method+path appears in the spec, and every non-`x-internal` spec path exists as a route
     (no drift in either direction);
   - no handler returns a bare `error(...)` — every failure carries an `ApiErrorCode`;
   - every collection endpoint accepts `limit`/`cursor` and returns `{ items, nextCursor? }` — a
     public list endpoint cannot ship unpaginated;
   - unknown/inaccessible resource ids return `404`, never `403` (the existence-concealment rule
     from Conventions), spot-checked per resource type;
   - every `routes/api/admin/**` handler calls a **platform-permission** guard on every exported
     method. After blocker #6 moves the org-assets route out, the admin tree is uniformly
     platform-scoped and this assertion is clean — the allowed set is `requireInstanceAdmin`,
     `requireManageCompute`, `requireManageInstanceUsers`, and `requirePermission` with a platform
     permission (four helpers, not one — don't write the test assuming `requireInstanceAdmin`
     only). This is the check that makes admin protection structural: the `/admin` layout guard
     never ran for endpoints, so today "all admin routes guard themselves" holds only by review.

   Without these, `x-internal` is an annotation someone remembers to write rather than a
   boundary the build enforces.

3. **Docs page** `/docs/api` rendering the public subset of the spec.

## Efficiency audit

Phase B says "extract the batched access filtering into `listVisibleDefinitions`" as if it were a
pure move. It is not — **the thing being extracted is the most expensive read in the app**, and
lifting it behind a public, paginated, PAT-reachable endpoint multiplies how often it runs. What
follows is what the current code actually costs and what v1 should change.

### The library list is O(orgs + projects), not O(page)

[library/+page.server.ts](../../packages/selva/src/routes/library/+page.server.ts) issues, per
request:

| Step                        | Calls                                      | Notes                                                           |
| --------------------------- | ------------------------------------------ | --------------------------------------------------------------- |
| `listOrgs` + `list`         | 2 (parallel)                               | both hardcoded `limit: 200`                                     |
| `listProjects` per org      | **N_orgs**                                 | one call per org, `limit: 200`                                  |
| `getOrgMember` per org      | **N_orgs**                                 | one call per org                                                |
| `getProjectMember` per proj | **N_projects**                             | one call per project — across _all_ orgs, not just visible ones |
| `listByProject` (grants)    | **N_platform-visibility projects**         | one call per platform project                                   |
| **Total**                   | **2 + 2·N_orgs + N_projects + N_platform** |                                                                 |

The comments call this "batched to avoid a per-project N+1 (§2c)", and it is genuinely better than
a naive loop — the org rows are fetched once and reused. But `Promise.all` over N single-row reads
is still N round-trips; it is a _concurrent_ N+1, not an eliminated one. At 5 orgs / 60 projects
that is ~130 queries to render one page.

**And the fetches run as `SYSTEM_CONTEXT`, not as the caller.** The library load reads orgs,
projects, memberships, and definitions with system reach and relies entirely on the in-process
`canView` filter for tenancy (the `/projects` load, by contrast, uses the caller's ctx). The
post-hoc filter is therefore **load-bearing for security**, not merely a perf artifact — which
raises the stakes on the extraction in Phase B: `listVisibleDefinitions` inherits the role of
tenancy boundary for a public PAT-reachable endpoint, and its accessible-project-set resolution
must be provably correct, not just fast.

Worse for v1: **the filtering happens after the fetch**. `meta.list(…, { limit: 200 })` pulls 200
published definitions, then discards every one whose project failed `canView`. Cursor pagination
over that is incorrect, not just slow — a page of 50 can return 3 items because the other 47 were
filtered post-hoc, and `nextCursor` reflects the pre-filter position. **A naive
`listVisibleDefinitions(ctx, {limit, cursor})` built on today's code would ship a broken
pagination contract.** The same applies to
[projects/+page.server.ts](../../packages/selva/src/routes/projects/+page.server.ts), which repeats
the identical pattern and additionally calls `listProjectMembers` per visible project when the
caller has `manage_projects`.

### Missing store primitives (the actual fix)

The platform layer has no bulk membership read. It already has the pattern —
`IUserProfileStore.getProfiles(ctx, userIds[])`
([userProfile/interface.ts:21](../../packages/platform/src/userProfile/interface.ts#L21)) is exactly
the right shape — it just was never applied to the rows the access rules consult:

- `IOrganizationStore.getOrgMembersFor(ctx, orgIds[], userId)` → `Map<orgId, OrgMember|null>`
  (replaces N_orgs calls with 1)
- `IProjectStore.getProjectMembersFor(ctx, projectIds[], userId)` → `Map<projectId, ProjectMember|null>`
  (replaces N_projects calls with 1)
- `IPlatformProjectGrantStore.listByProjects(ctx, projectIds[])` (replaces N_platform calls with 1)

That collapses the library load from `2 + 2·N_orgs + N_projects + N_platform` to a constant **5**,
with no change to the access semantics — `canView` still evaluates against the same rows, they just
arrive in three queries instead of a hundred. Both adapters implement it naturally (`WHERE
project_id = ANY($1) AND user_id = $2` on Supabase; a filter over the loaded JSON on local).

**Recommendation: this is a Phase B prerequisite, not a follow-up.** Extracting the helper first and
optimizing later means the optimization has to be redone against two callers (helper + load
functions) plus a live public endpoint, and the pagination bug ships in the meantime.

### Push visibility into the query where possible

The constant-5 version still over-fetches: it reads every project in every org to filter most of
them away. The real fix is `listVisibleDefinitions` resolving the accessible project-id set _first_
(one indexed query per the above), then passing `projectIds` as a filter into
`meta.list` — so the database applies both the visibility filter and the cursor, and the page
boundary is correct by construction. `DefinitionListOptions` already carries `statuses`; adding an
optional `projectIds` filter is additive and unblocks correct pagination.

This is the one place where "extract the helper" should become "write the helper properly" — it is
the difference between v1's flagship list endpoint being paginated in name and in fact.

### Missing endpoints that force clients into N+1

Independent of the above, four gaps make an API consumer issue calls it shouldn't have to. Three
are already in the plan; the fourth is not:

- `GET /definitions/{guid}/schema` — **already planned**, and the single most important one: without
  it a client must solve blind or scrape the preview page.
- `GET /projects/{id}` and `GET /orgs/{orgId}/members` — **already planned**.
- **`GET /definitions?projectId=` must return enough to avoid a detail fetch per row** — resolved
  below.

### The definition list row — RESOLVED

**Ship a narrow `DefinitionListItem` DTO next to `DefinitionRecord` in
[platform/src/definitions/types.ts](../../packages/platform/src/definitions/types.ts). No
`liveVersionNumber` join.**

```ts
interface DefinitionListItem {
	guid: string;
	projectId: string;
	displayName: string;
	description?: string;
	category?: string;
	tags?: string[];
	coverImage?: string;
	status: DefinitionStatus;
	solveCount: number;
	liveVersionId: string | null;
	updatedAt: string;
}
```

That field set is not invented — it is exactly what the UI has proven it needs. `DefinitionCard`
and `ToolListView` between them render `guid`, `coverImage`, `displayName`, `description`, `tags`,
`status`, `solveCount`, `updatedAt`, and the parent resolves `projectId` to a name chip; search
additionally reads `category`.

Two reasons this is a DTO rather than `DefinitionRecord`:

- **Both list pages currently ship `ownerId`, `createdBy`, `updatedBy`, and `solveCacheLimit` to
  the browser, and no card reads any of them.** Re-exporting `DefinitionRecord` from a versioned
  public endpoint bakes that leak into a contract where the additive-only policy means removing a
  field needs v2. Narrowing is free now and impossible later.
- `solveCacheLimit` is documented as "Dormant" in the type itself — publishing a dormant field is
  a promise you didn't mean to make.

**Why no `liveVersionNumber`:** it is not a native column. `DefinitionRecord` carries
`liveVersionId` (a pointer) but no number, so the field needs a join in **both**
`SupabaseDefinitionStore.list` and `LocalDefinitionStore.list`. Nothing in the product shows a
version number in a list today — the only consumer is `VersionsSection.svelte:52`, which resolves it
lazily client-side when a drawer opens, and the versions API itself returns `liveVersionId` and lets
the client correlate. `liveVersionId` in the row keeps that pattern available without the join.

If a version number in list rows later earns a use-case, adding it is additive — **but the join must
reuse the schema-less projection** (`DEFINITION_VERSION_COLUMNS`, not `…_WITH_SCHEMA`). Schema blobs
are "hundreds of KB per row" by the provider's own comment
([SupabaseDefinitionStore.ts:24-29](../../packages/providers/supabase/src/data/SupabaseDefinitionStore.ts#L24-L29));
a careless join regresses that into a 200-row list response. Both providers strip `schema` from
list paths today and a store-suite test pins it — keep it that way.

### Non-issues, checked

- **`listVersions` omitting `schema`** is correct and deliberate — the interface documents it. The
  new `GET /versions/{versionId}/schema` endpoint is what serves the blob, on demand. Keep it that
  way; do not "helpfully" inline schema into the versions list.
- **The four per-request hook reads** are covered under "Auth mechanics" above — a PAT-path concern,
  not a v1 route concern.
- **`/api/compute` solve path** does not have this problem: it resolves one definition by guid and
  gates it directly. No N+1 there.

### Verification to add

- Assert query counts, not just correctness: a test double counting store calls for
  `listVisibleDefinitions` over a 5-org / 60-project fixture must show a **constant** count
  independent of N.
- Paginate the real endpoint with `?limit=5` across a dataset where the caller can see a minority of
  definitions; every page must return 5 items until the last. This is the check that catches
  post-hoc filtering.

## Blockers found during validation — ALL RESOLVED

Six things that had to be decided before Phase A. All six are now settled; each entry keeps its
evidence and records the decision. #1, #2, #3 and #6 were diagnosed with a fix specified (work
items, not decisions); #4 and #5 were genuine decisions and are marked RESOLVED inline.

### 1. `GET /api/projects` has no callers and no access filtering

The handler ([api/projects/+server.ts:36](../../packages/selva/src/routes/api/projects/+server.ts#L36))
is `listProjects(ctx, ctx.actingOrgId, { limit: 200 })` — **every project in the acting org, with
no `canView` filter**. Meanwhile [projects/+page.server.ts](../../packages/selva/src/routes/projects/+page.server.ts)
does full per-project `canView` filtering. Repo-wide grep: the UI only ever calls `POST
/api/projects`; the `GET` is dead code.

So "moved" is the wrong status for it. Marking it moved would promote an unfiltered,
never-exercised listing into a **PAT-reachable public endpoint** — a read that returns projects the
caller cannot open in the UI. `GET /api/v1/projects` must be authored against the same visibility
rules as the page load (i.e. it is **NEW**, sharing Phase B's helper), not lifted. Its whole
`limit: 200` / `{ projects: … }` shape is being replaced anyway.

Check the same question for every other endpoint the plan calls "moved": _is this handler currently
exercised by the UI, and does it filter what a public caller may see?_ Dead handlers carry no
evidence that they are correct.

### 2. Colocated route tests move with their routes

Ten test files in seven `__tests__/` directories live under the moving trees and import the
handler relatively (`from '../+server.js'`):

- `api/compute/__tests__/` (3 files), `api/definitions/__tests__/upload-schema-gate`,
  `api/definitions/[guid]/share-links/__tests__/mint-revoke`, `api/invites/__tests__/mint-hash`,
  `api/orgs/[orgId]/members/[userId]/__tests__/` (2 files), `api/files/[...path]/__tests__/`
- `admin/api/users/[id]/__tests__/sole-admin-sequencing`

They move with their directories and the relative imports keep working — but
`mint-revoke.test.ts` imports `DELETE` from `'../[linkId]/+server.js'`, so any restructuring inside
a route dir breaks it. `api/files/[...path]/__tests__/` must **not** move (that route stays put).
Add these to Phase A's file list so the move is planned rather than discovered by a red suite.

### 3. `/api/v1/orgs/{orgId}/invites` — the handler ignores `orgId`

Invites are scoped **entirely** by `ctx.actingOrgId` today
([invites/+server.ts:40](../../packages/selva/src/routes/api/invites/+server.ts#L40), and the
`[id]` DELETE re-lists `listByOrg(ctx, ctx.actingOrgId)` to confirm ownership before revoking).
Adding `{orgId}` to the path does not make the handler org-parametric — it introduces a URL
parameter the handler does not read.

Do what the org-members route already does: add the explicit tenancy check
(`ctx.actingOrgId !== orgId` → 403) to all three invite handlers as part of the rename. Without it,
`/api/v1/orgs/{anyOrgId}/invites` silently returns the caller's own org's invites — a confusing lie
for a public API, and a genuine bug the moment URL-prefix tenancy lands.

Same applies to `/api/v1/orgs/{orgId}/compute`, which is likewise `actingOrgId`-implicit.

### 4. `/api/v1/orgs/{orgId}/compute` is flag-gated — RESOLVED: `x-internal`

Both methods 403 when `ALLOW_ORG_COMPUTE_OVERRIDE` is off
([api/org/compute/+server.ts:45-52](../../packages/selva/src/routes/api/org/compute/+server.ts#L45-L52)),
and the flag defaults to **off** (`SELVA_FLAG_ALLOW_ORG_COMPUTE_OVERRIDE`, `readBool(…, false)` in
[create-selva-providers.ts:151](../../packages/server/src/providers/create-selva-providers.ts#L151)).

**Decision: `x-internal`.** It manages encrypted-at-rest infrastructure credentials
(`IComputeServerStore` holds `apiKey` under `SELVA_AT_REST_KEY`), no CLI/MCP use-case in the token
plan needs it, and an endpoint whose _existence_ depends on instance configuration is a poor public
contract. Public-but-conditional would mean publishing a 403 that most instances always return.

Two things to fix while moving it, both found during validation:

- **The GET handler has no in-repo consumer.** `team/compute/+page.server.ts:35-72` duplicates its
  logic in a load function (same `ownServers` strip, same catalog map, plus `isGlobalDefault` and
  `overrideEnabled`). Per blocker #1's rule — _dead handlers carry no evidence that they are
  correct_ — either delete the GET or switch the load to it. Do not move it unexamined.
- **PUT is a full replace with no `If-Match`**, and its key-preservation fallback is keyed on
  `s.id`, so changing a server's id in the UI silently drops its stored key. Out of scope for this
  plan, but record it — it is a data-loss path on a credential store.

### 5. Anonymous share solving — RESOLVED: anonymous is the design; compute stays outside v1

The compute handler carries an anonymous share-token branch (`tryResolveShareToken` → synthetic
ctx), and the mint dialog produces `/library/{guid}?token=share_…` URLs clearly meant for
recipients without accounts
([MintShareLinkDialog.svelte:83](../../packages/selva/src/routes/projects/_components/MintShareLinkDialog.svelte#L83)).
But the hook's deny-by-default gate has **no share-token carve-out** — `publicApis` is only
`/api/health`, self-gating only `/api/files/` — so an anonymous visitor is redirected to login at
`/library/{guid}` and an anonymous `POST /api/compute` 401s before the handler runs.

**This was not a coin-flip between two intents — the evidence is one-sided.** Anonymous access is
the documented design in six independent places:

- [Permissions.md:469](../../packages/selva/specs/Permissions.md#L469) — share links grant access to
  one definition + channel "**without requiring an account**… one mechanism, both use cases
  (sharing a draft for review; embedding a definition in a public iframe)"
- [Permissions.md:169](../../packages/selva/specs/Permissions.md#L169) — "Anonymous access is not a
  project flag — it's delivered via per-definition share links"
- [access/rules.ts:58](../../packages/platform/src/access/rules.ts#L58) — "Anonymous access is
  delivered via share-link tokens"
- [shareLinks/types.ts:5](../../packages/platform/src/shareLinks/types.ts#L5),
  [interface.ts:6](../../packages/platform/src/shareLinks/interface.ts#L6) — "without an account",
  "granting **unauthenticated** access"
- [SupabaseShareLinkStore.ts:85](../../packages/providers/supabase/src/data/SupabaseShareLinkStore.ts#L85)
  — "token resolution must work **for anonymous requests too**"
- [security-headers.test.ts:24](../../packages/server/src/http/__tests__/security-headers.test.ts#L24)
  — "iframe embedding is a **product requirement**"

The synthetic ctx confirms it: `{ userId: '', actingOrgId: project.orgId, platformPermissions: [],
orgPermissions: [], system: true }` ([resolve.server.ts:98-104](../../packages/selva/src/lib/server/shareLinks/resolve.server.ts#L98-L104))
— no user, zero permissions, authorization _is_ the token. And the tests pass an `anon()` fixture
with no `user` and no `ctx` (`endpoint-share-cap-and-rate-limit.test.ts`, via
[fixtures.ts:584-586](../../packages/selva/src/lib/server/__tests__/fixtures.ts#L584-L586)) — they
call `POST` directly, bypassing the hook, which is exactly why the gap was never caught.

**It is aspirational, not a regression.** `git log -S"/library" -- hooks.server.ts` returns nothing;
the share-link feature commit `7adce76b` touched the resolver, routes, stores, and config but
**not** `hooks.server.ts`. There is a second unfinished half: `library/[guid]/+page.server.ts:78-80`
returns `shareToken` "so `/api/compute/solve` calls can include it", but `+page.svelte` never reads
it — so even with the hook opened, every shared solve would 401.

**Decision: `/api/compute` and `/api/compute/schema` stay OUTSIDE v1, unversioned, alongside
`/api/files`.** Documenting the branch as dormant (the earlier "logged-in-only" option) would write
a v1 contract that contradicts the spec and then require breaking it to honour the spec later.

Consequences for this plan:

- The **Compute utilities** table moves out of the v1 map into "Deliberately outside v1".
  `POST /api/v1/definitions/{guid}/solve` remains v1's solve path (cookie + PAT); it extracts the
  same core (Phase C) but never carries a share token.
- The "Auth mechanics" #3 invariant is **restated, not weakened**: every `/api/v1/*` route requires
  a fully-populated `locals.ctx`. Anonymous-capable endpoints live outside the prefix — now two of
  them (`/api/files/`, `/api/compute`) rather than one. The `startsWith('/api/v1/')` PAT gate stays
  unconditional, which is the entire point.
- Wiring anonymous sharing up (hook carve-out + threading `data.shareToken` into the solve fetch) is
  **its own piece of work, not part of this plan** — but it is now unblocked by it rather than
  contradicted. Record it as a follow-up.

Token-plan Phase 2's PAT branch must **pass through** `Authorization: Bearer` values that aren't
`sk_…` (share tokens ride the same header) instead of rejecting them.

### 6. `admin/api/orgs/[id]/assets/[kind]` is a tenant route in the admin tree

It's gated by **org-scoped** `requireManageOrgMembers` — the only admin endpoint not behind a
platform permission — while the `/admin` UI shell it's reachable from requires a platform
permission to enter. Net effect: the org admins the route is _for_ can't reach it. Moving it to
`/api/admin/*` cements the mismatch and breaks the Phase D "admin = platform-guarded" conformance
assertion. Move it to `/api/v1/orgs/{orgId}/assets/{kind}` instead (endpoint map above), with the
standard tenancy check; the admin UI keeps working since instance admins hold org reach through
their own membership or the fallback.

## Interaction with token-plan.md

- Token plan **Phase 4 is superseded** by this plan (no wrapper layer; this IS the managed API).
- PAT acceptance (token plan Phase 2) gates on `pathname.startsWith('/api/v1/')` exactly, and
  populates the same `locals.user` / `locals.ctx` the cookie path builds — that is what makes every
  v1 handler bearer-capable without modification. See "Auth mechanics" above. The acting-org
  question is now **settled here, not in Phase 2**: PATs carry an explicit `orgId` and minting is
  rejected when the user's only org is the instance-admin fallback. Phase 2 still decides whether
  to cache context per token, and must **pass through non-`sk_` bearer values** (share tokens ride
  the same header — blocker #5).
- Token mint/management routes land at `/api/v1/tokens` from the start.
- Per-token rate limiting stays in the token plan; this plan only guarantees every v1 endpoint
  flows through guards that can consume `ctx.apiScope`.
- Build order: **Phase A/B of this plan first**, then the token plan — PATs should launch against
  the final surface, and the OpenAPI spec (Phase D) can document bearer auth in one pass.
- **The CLI is the first PAT consumer, ahead of MCP** (token-plan Phase 5). `selva projects list`,
  `definitions list`, `definitions schema`, `definitions upload`, `solve` are all tenant-scope
  `/api/v1/*` calls — none need `/api/admin/*`, which is what keeps the cookie-only admin split
  free. A PAT never widens permissions (token-plan's intersection rule), so CLI output is scoped to
  what its minting user can already see; `all-projects-admin` is the one deliberate exception and
  is read/solve only.

## Resolved: the three non-blocking questions

All three adopted at their stated lean. Each is **additive under the v1 change policy**, so none of
them constrains the surface — shipping without them costs nothing that a later minor can't add.

- **`GET /definitions` ships filter-only in v1.0** — no free-text `q`. There is no store-level
  search primitive; the library page filters client-side over an already-fetched page
  (`library/+page.svelte:58-71`). Adding `q` means designing a search path in both providers, which
  is its own piece of work and not on v1's critical path.
- **No `.gh` blob download URL on version detail in v1.0.** Version metadata + `changeNote` only.
  Add deliberately if a use-case appears.
- **Solve stays synchronous** — no `202 Accepted` + polling. Matches Rhino.Compute's actual
  behaviour; revisit if and when queueing lands.
