# Bug hunt, 2026-11-13

Repo-wide bug hunt at `3990e572` (beta). Bugs only, no style. Each finding below survived an
attempt to refute it. Severity is the impact on a deployment that follows the docs.

## How it was checked

- **Baseline:** CI green on `226f6c57` (Test, E2E, CodeQL). HEAD is the `[skip ci]` version bump on top.
- **Hunters:** 24, each blind to the others. 18 slice hunters read about 80k of the 229k source
  lines (plus all 33 migrations) in full; 6 invariant hunters each followed one rule across the
  whole repo: authorization at every entrypoint, the data layer as boundary, atomic guarded
  invariants, secrets and personal data, erasure and offboarding, outside input. Models: Fable for
  the invariant hunters and the six riskiest slices (Supabase SQL, Supabase stores, auth
  providers, `@selvajs/server` http/oauth, access guards with `/team`, app routes); Opus for the
  other twelve slices.
- **Refutation:** a Sonnet agent per hunter tried to disprove every finding and checked each
  assumption the hunter made about code outside its slice. Fable settled the verdicts that turned
  on semantics and judged the false assumptions, which produced 14 more findings (ids with `.A`).
  3 findings were refuted.
- **Reproduction:** 151 of 177 findings were reproduced as tests in the repo's own vitest harness,
  in a throwaway worktree. Supabase SQL ran on PGlite with every migration applied, so RLS and RPC
  findings ran real Postgres. C# findings ran in scratch projects that link the plugin source.
  The orchestrator reran all 218 repro tests in one pass. The 57 failing ones are failing-first
  tests whose failure message shows the bug; the passing ones assert the buggy behaviour. Two
  tests need a live GoTrue and timed out, so the Supabase OAuth finding stays read-only. The C#
  repros were rerun by their refuters, not in this pass.
- **Spot check:** the orchestrator opened the cited code for every High finding. The RLS findings
  matter because the anon key is publishable: the `selva_rls_is_the_boundary` migration header
  says so, and `selva_initial.sql` grants all on `selva` tables to `authenticated` and exposes the
  schema to PostgREST.
- **Repros:** saved to `.claude/bug-hunt-2026-11-13/` (gitignored): `worktree/` mirrors the repo
  paths of every `__hunt__` test, `scratch/` holds SQL, shell and C# repros, `rerun-results/` the
  JSON reports.

**Slices not hunted** (budget of 24 hunters): `Plugin/Selva.Drawing`, `Selva.App`, `Selva.Rhino`,
`Selva.Schema`, `Selva.Setup`, `Selva.Slva`; the plugin's Display, Drawing, FileIO, ComputeIO,

**Not read in full:** Svelte markup below the script block in parts of `routes/team`, `routes/admin`

### High

**H1. `definition_versions.file_key` is unconstrained, and the server reads and deletes whatever it names with the service role.**  
`packages/providers/supabase/supabase/migrations/20261101160000_selva_rls_is_the_boundary.sql:231` · reproduced · H01.0, H02.0, H02.A0, INV-A.0, INV-B.0 · parafa lead 2

- Trigger: A project editor in any org sends a PostgREST insert (or update) on selva.definition_versions for their own definition with file_key='definitions/<other guid>/versions/v1.gh', then solves its draft or deletes that version in the app.
- What goes wrong: RLS never checks file_key and the server trusts it: solve and load-for-render call storage.get(version.fileKey), deleteVersion calls storage.delete(version.fileKey), all with the service role. Another tenant's .gh is solved and schema-extracted, or deleted. Guids leak through URLs and colleagues' recent_runs.
- Fix: Pin file_key in SQL (check or trigger: 'definitions/'||definition_guid||'/versions/v'||version_number||'.'||file_ext), take UPDATE on file_key away from authenticated, and derive the key from guid and version number in the server instead of reading it from the row.
- Also at: `packages/server/src/definitions/definition-service.ts:201`

**H2. `/setup` serves the pinned `BOOTSTRAP_INSTANCE_ADMIN_EMAIL` to anonymous visitors, and the action accepts that email as the only proof.**  
`packages/selva/src/routes/setup/+page.server.ts:40` · reproduced · INV-D.0

- Trigger: No instance admin yet (fresh install, or the documented lockout recovery), password auth, BOOTSTRAP_INSTANCE_ADMIN_EMAIL set. An anonymous visitor GETs /setup, reads bootstrapEmail from the page data, POSTs it back with a password of their own.
- What goes wrong: The public load serializes the pinned admin email in every auth mode (the markup shows it only for proxy auth). The action checks nothing but that email, so the stranger gets 303 /admin and ALL_PLATFORM_PERMISSIONS. The pin is the documented guard for internet-reachable hosts and is flagged sensitive in the config manifest.
- Fix: Return bootstrapEmail only when the provider is proxy-only (the one branch that renders it). For password setup, gate the claim on something the visitor cannot read from the page, e.g. a one-time setup token printed by the CLI or log at boot.

**H3. Org membership without consent: the `org_members` insert and update policies check only the role, not the user, joined_at, deleted_at or permissions.**  
`packages/providers/supabase/supabase/migrations/20261101160000_selva_rls_is_the_boundary.sql:315` · reproduced · H02.2, INV-A.2, H02.A1, H06.4, INV-B.7 · parafa lead 1

- Trigger: An org admin POSTs /rest/v1/org_members {org_id: own org, user_id: <any user>, role:'member', joined_at:'1970-01-01'} with their session JWT. User ids are exposed as owner_id on public definitions and to former colleagues.
- What goes wrong: may_set_org_role lets an admin insert a member row for anyone, with no invite. hooks.server.ts:132 builds every session from the oldest live membership (findUserMembership, joined_at asc) and there is no org switcher, so the victim now acts in the attacker's org and loses their own org's routes and org-visible projects.
- Fix: Revoke INSERT on selva.org_members from authenticated: the app only adds members as service role (accept-invite, admin users). If session inserts must stay, force joined_at = now() and require a matching accepted invite.
- Also at: `packages/selva/src/hooks.server.ts:132`, `packages/providers/supabase/supabase/migrations/20261101160000_selva_rls_is_the_boundary.sql:321`

**H4. A project owner can move the project into another org or make it public through PostgREST, and can add users from outside the org.**  
`packages/providers/supabase/supabase/migrations/20260817160000_rls_matches_access_rules.sql:43` · reproduced · H01.2, H02.1, INV-A.1, INV-B.2, INV-B.6

- Trigger: A project owner sends PATCH /rest/v1/projects?id=eq.X with org_id=<another org> (org ids show on public project rows and selva-public branding paths), then inserts a share_links row whose token_hash is the sha256 of a token they picked.
- What goes wrong: The UPDATE policy checks only is_project_owner(id), so org_id and visibility are free. The project appears in the other org, and solves pick compute by project.orgId, so share-token solves run the mover's definition on that org's servers. A plain member can also set visibility='public', and project_members accepts users outside the org, who keep access after the inserter is offboarded.
- Fix: Reject org_id changes (trigger, or WITH CHECK against the stored row), require is_org_admin(org_id) for a change to 'public', and require the user of a project_members insert to be a live member of the project's org.
- Also at: `packages/providers/supabase/supabase/migrations/20260817160000_rls_matches_access_rules.sql:59`

**H5. A removed or demoted project creator can make themselves owner again through PostgREST.**  
`packages/providers/supabase/supabase/migrations/20261101160000_selva_rls_is_the_boundary.sql:110` · reproduced · H01.1, H06.0, INV-B.1

- Trigger: A user creates a project, is later removed from it or demoted to viewer while still an org member, then upserts their own selva.project_members row with role 'owner' through PostgREST.
- What goes wrong: The 'seeding an owner row' and 'reactivating a seeded owner row' policies pass on projects.owner_id = auth.uid(). owner_id is stamped at creation and never updated, so the removed creator is owner again and reads and edits the private project. The app has no such path: canManage needs a live owner row.
- Fix: Limit the owner_id branch of may_seed_project_owner to creation, e.g. require that the project has no project_members row yet, or seed the creator inside a definer create-project RPC. Keep only the org-admin reclaim branch for later writes.

**H6. Invites keep authority their inviter has lost, and the invites insert policy lets an admin forge the inviter and expiry.**  
`packages/server/src/handlers/invites.ts:243` · reproduced · H16.0, H07.0, INV-B.A0

- Trigger: Org owner + instance_admin mints an invite {orgRole:'owner', permissions:['instance_admin']} to an alt email, then has instance_admin revoked and is demoted to member. The alt account then accepts the link.

**H7. The update launcher runs a fixed `/tmp/selva-update-runner.sh` it may not have written.**  
`packages/selva/src/lib/server/updateRunner.server.ts:60` · reproduced · H09.0

- Trigger: Another local account on the host creates /tmp/selva-update-runner.sh (mode 644, its own) before an update, or after /tmp is cleaned. An instance admin then clicks Update.
- What goes wrong: The launcher always uses the fixed path RUNNER=/tmp/selva-update-runner.sh. `cat >` fails with EACCES, chmod fails, and nothing checks either. `setsid bash "$RUNNER"` then runs the planted file as the app user, which holds SELVA_AT_REST_KEY and the Supabase service key. A second deployment on the same host under another user runs the first one's stale runner the same way.
- Fix: Create the runner with mktemp, inside the deployment dir or a 0700 dir. Run the launcher under `set -e`, or check that cat and chmod succeeded before setsid. Delete the runner when it finishes. Do the same for /tmp/selva-health.$$.

**H8. Get File / Get Image on Compute open any server-local or UNC path a solve caller sends.**  
`Plugin/Selva.GH/Features/FileIO/Services/FileImporter.cs:61` · read-only · INV-F.0

- Trigger: Any solve caller, a share-link visitor included, posts a File/Image input value {"file":"C:\\..." or "\\\\host\\share\\a.png","type":"path","fileEnding":".webp"} (or a bare path string) to /api/v1/compute or /definitions/{guid}/solve.
- What goes wrong: The app forwards the value unchanged; on Compute, Get File/Get Image treat it as a local path. ImageInputResolver.ResolvePath (line 76) returned the bytes of a non-image file; Get File answers 'File not found: <path>' (existence oracle); a UNC path makes the Compute account authenticate to the caller's SMB host. - Fix: Refuse type 'path' and bare strings when HeadlessGuard.IsHeadless (FileInputParser.Validate/Parse, ImageInputResolver, TextureInput); only base64 and guarded url are valid from a web solve. Drop the path from the error text.

## Found by staging a real self-update

Run locally for #202: a Linux container under pm2 7.1.2, a throwaway npm registry, a scaffolded
deployment, then in-app updates to a higher version and to one that refuses to boot.

- **The update runner was killed by pm2's tree kill (High, reproduced, fixed).** The runner called
  `pm2 stop` while still a child of the app. pm2 7 lists the app's descendants then and SIGKILLs
  the survivors after its kill timeout, runner included: the app stayed stopped on the old
  version. It needs the registry to answer inside the launcher's one-second pause, which a real
  host usually misses. `packages/selva/src/lib/server/updateRunner.server.ts`: the runner is now
  orphaned before it runs a line.
- **The app never exited on SIGINT or SIGTERM (Medium, reproduced, fixed).** adapter-node closes
  the server and waits for the event loop to empty; timers kept it alive, so every stop took
  pm2's 10 s kill timeout and ended in SIGKILL. `hooks.server.ts` now flushes the metric sink and
  exits on `sveltekit:shutdown`: 1.1 s instead of 10.4 s.
- **Confirmed working:** the update end to end, the rollback after a failed health probe, the
  setup link from the scaffold, and recovery with `selva update` on the CLI.
- **Open, small:** `selva update` has no non-interactive flag and exits 13 without a terminal;
  a failed probe prints its status twice (`HTTP 000000`).

## Decisions

- **Sessions do not write `selva` tables.** Patching each write policy was rejected: some app rules
  cannot be stated in SQL (env feature flags, the compute URL guard, key sealing), and a direct
  write never emits its audit event, so an org admin could reclaim a project through PostgREST
  with no `project.reclaimed` row. `anon` and `authenticated` keep SELECT under RLS; the stores
  write with the service role after the app's gates, as storage objects always have. Every write
  call site was checked for an app-side gate first, and none leaned on RLS alone. This closes H1,
  H3, H4, H5, M1, M3, M4, M5, M33, L1 and L34. Real data invariants stay in the schema, because
  they bind the service role too: a version's `file_key`, a project's org, slug uniqueness among
  live rows.
- **`instance_admin` and tenant content on Supabase (M6).** The write half is gone with the
  policies. The read half is gone too: `visible_project()` has no admin branch, and the management
  guards read a project as system for an instance admin. Staff still read the share-link roster,
  which is management data.
- **`/setup` proves the claimant with a setup token (H2).** An HMAC of a fixed label under
  `SELVA_HMAC_KEY`, printed by the scaffold and by `selva setup-url`, never logged. It needs no
  stored state and is the same on every instance. The pinned email stays as a second check.
